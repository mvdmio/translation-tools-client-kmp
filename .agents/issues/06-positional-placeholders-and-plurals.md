# Runtime client does not handle Android `%1$s` or `<plurals>`

Category: enhancement
Status: needs-triage

**Source:** jewel-app colleague, 2026-08-18

## Summary

Two runtime gaps for Android XML consumers. They do not affect Gradle sync: values go through verbatim.

1. The runtime client substitutes only `{named}` tokens (camelCase). It does not substitute Android positional formats such as `%1$s` and `%1$d`. jewel-app has nine of those.
2. The Android parser skips `<plurals>`. jewel-app has no `<plurals>` today. It pluralizes by hand in `WorkScreen.kt` and `WerksoortScreen.kt`.

## Why it matters

Sync-only adoption does not need this. Runtime refresh of jewel-app strings that use `%1$s` would leave those tokens in the displayed text. `<plurals>` would stay a future gap if they start using the Android resource type.

## What we verified

[`PlaceholderTests.kt`](../../src/commonTest/kotlin/io/mvdm/translationtools/client/placeholders/PlaceholderTests.kt): `{userName}` works; `{0}` is not a token.

[`PlaceholderSubstitution.kt`](../../src/commonMain/kotlin/io/mvdm/translationtools/client/placeholders/PlaceholderSubstitution.kt) only walks `{name}` segments.

[`AndroidStringResourceParser.kt`](../../gradle/translationtools-plugin/src/main/kotlin/io/mvdm/translationtools/gradle/AndroidStringResourceParser.kt) records `"plurals are not supported"` and skips the resource. Tests assert that.

README already says the tool skips `<plurals>` and `<string-array>`.

## Suggested directions

- Positional format: either teach the runtime (and codegen) to substitute `%1$s` / `%1$d`, or tell Android consumers to switch those nine strings to `{named}` tokens.
- Plurals: leave skipped until a consumer actually ships `<plurals>` they want in TranslationTools.
